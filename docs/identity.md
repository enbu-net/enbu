# TPM key generation

This page states what enbu requires of the TPM keys behind a hardware Identity
on Linux and Windows, and which tests check each requirement. Secure Enclave
keys on macOS are generated by the Secure Enclave and are not covered here.

## Requirements

1. **The TPM generates the private key.** enbu creates the encryption key and
   the signing key with `TPM2_Create` under the owner-hierarchy storage primary
   (the `ECCSRKTemplate` primary, re-derived from the owner seed when a process
   first needs it, and shared by every key that process loads).
   The command carries no caller sensitive data, so the private scalar comes
   from the TPM's own random number generator. enbu never generates a TPM key
   on the host and never calls `TPM2_GetRandom` for key material.
2. **The key cannot leave the TPM.** Both keys have `fixedTPM`, `fixedParent`
   and `sensitiveDataOrigin` set. The encryption key can only run
   `ECDH_ZGen` (P-256, policy: command code and auth value); the signing key can
   only sign (ECDSA P-256, SHA-256). Neither can be duplicated.
3. **Imported keys are refused.** enbu never calls `TPM2_Import`,
   `TPM2_LoadExternal` or `TPM2_Duplicate` for an Identity. When a key is
   loaded, its public area must equal the template byte for byte, including
   `fixedTPM` and `sensitiveDataOrigin`. A conforming TPM refuses to import an
   object with `fixedTPM` or `fixedParent` set (TPM 2.0 Part 3, TPM2_Import), so
   a key that loads under the storage primary with `fixedTPM` set was generated
   by that TPM. This rests on the TPM conforming to the specification; enbu does
   not verify the TPM's manufacturer or its endorsement key.
4. **Every private-key operation runs on the TPM that holds the key.**
   Decryption sends `ECDH_ZGen`, and signing sends `TPM2_Sign`, to the device
   the backend opened: `/dev/tpmrm0` (the kernel resource manager; never the raw `/dev/tpm0`) on Linux and TBS on
   Windows. The device is recorded in the Identity metadata. The saved blobs load
   only under the storage primary of the TPM that created them.
5. **Secrets are encrypted on the bus.** The `ECDH_ZGen` result, the sealed
   ML-KEM seed going into `TPM2_Create` and coming out of `TPM2_Unseal` travel
   under AES-128-CFB parameter encryption, in sessions salted to the storage
   primary. The primary's Name is pinned in the metadata when a key is created
   (`tpm_parent_name`), and a key is refused under any other primary, or
   without a pin. The primary's Name must also be the hash of the public area
   it came with, and that area must match the storage template. These checks
   do not authenticate the primary when a key is created: enbu pins whichever
   primary the TPM reports then, as trust on first use, because it has no
   endorsement key chain to check it against. From then on, a session is never
   salted to any other primary.
6. **Host randomness is not used for TPM keys.** The host's `crypto/rand` (the
   OS CSPRNG) supplies session nonces and salts, age file keys and ephemeral
   shares, local reference IDs, and the keys of the software fallback (X25519
   and Ed25519 in the OS keyring). None of these is a TPM private key.

The quality of the TPM's random number generator is the TPM vendor's
responsibility (for example FIPS 140 or Common Criteria certification). enbu
does not test it.

## Tests

| Requirement | Test | Runs on |
|-------------|------|---------|
| 1, 2, 4 | `TestTPMIdentityIsGeneratedAndUsedInTheTPM`, `TestTPMSignerIsGeneratedAndUsedInTheTPM` record every command: `TPM2_Create` has empty sensitive data, no import command is sent, and decryption and signing reach the TPM | test vTPM |
| 3 | `TestTPMRefusesImportedSoftwareKeys` imports a software P-256 key and checks that neither `Load` nor `LoadSigner` accepts it | test vTPM |
| 4 | `TestTPMKeyDoesNotLoadOnAnotherTPM` | test vTPM |
| 5 | `TestTPMSimulatorEncryptsSecretsOnTheBus` records every response and checks that neither the ECDH result nor the seed appears in the clear | reference TPM simulator (Linux, cgo) |
| 5 | `TestTPMRefusesAnotherStoragePrimary`, `TestTPMPrimaryNameMustMatchItsPublicArea` | test vTPM |
| 1, 3, 4 | `TestTPMNativeKeyOrigin` repeats the recording checks on the host TPM, and checks that the TPM refuses to import a software key marked `fixedTPM` | real TPM |

The test vTPM computes the HMAC of a parameter-encrypted command wrongly, so
the tests that use it turn parameter encryption off; the reference simulator
from go-tpm-tools covers it instead.

The test vTPM also imports a key marked `fixedTPM` without complaint, so only
`TestTPMNativeKeyOrigin` checks the TPM's side of requirement 3. Run it on a
Linux or Windows machine with a TPM 2.0:

```bash
ENBU_TEST_NATIVE_IDENTITY=1 go test -v -count=1 -run '^TestTPMNative' ./pkg/identity
```

Hosted CI runners have no TPM, so these native tests are skipped there.

## Hybrid post-quantum identities

New hardware identities are hybrid ML-KEM-768 + P-256 (`age1tagpq1…`), because
TPMs and the Secure Enclave APIs enbu uses cannot run ML-KEM yet. Decryption
needs both halves:

- **P-256** is the TPM key above, with every requirement unchanged.
- **ML-KEM-768** runs on the host. Its 64-byte seed is generated by the host's
  `crypto/rand` and sealed in a keyedHash object under the same storage primary,
  with `fixedTPM` and `fixedParent` set (`sensitiveDataOrigin` is clear because
  the host supplies the data). The seed is unsealed into host memory only to
  load the identity. When a sealed object is loaded, its public area must equal
  the template. Like the ECDH results, the seed crosses the TPM interface
  only under parameter encryption (requirement 5).
  The Secure Enclave keeps no sealed data, so on macOS the seed is kept in the
  Keychain.

Requirement 1 is about keys: the sealed seed is data, so its `TPM2_Create`
carries sensitive data, and requirement 6 covers its randomness.

| Check | Test | Runs on |
|-------|------|---------|
| The seed is sealed, reloads, and a blob without `fixedTPM` or with a damaged private part is refused | `TestManagerCreatesHybridTPMIdentityWithSealedSeed` | test vTPM |
| Another TPM cannot unseal the seed | `TestSealedSeedDoesNotUnsealOnAnotherTPM` | test vTPM |
| Hybrid decryption uses the TPM's ECDH and needs the matching ML-KEM key | `TestHybridIdentityOnTPM`, `TestHybridHardwareIdentityUsesBothKeys` | test vTPM / software |

## One connection per process

Creating the storage primary is a key generation, which takes a firmware TPM
tens to hundreds of milliseconds, and each open of the TPM costs a round trip
through TBS on Windows. The keys one process loads (the identity, its sealed
seed, the retained identities of a key update, and the signing key) share one
TPM connection and one primary. The last key to close flushes the primary and
closes the connection. `TestTPMKeysShareOneConnection` checks that loading an
identity, its seed and the signer opens the TPM and creates the primary once.
